Test4Test production deployment

Current production target

- Repository: omatthew-tech/Test4Test
- Production branch: ReDesign (case-sensitive)
- Cloudflare Worker: test4test-redesign
- Custom domain: test4test.io
- Build command: npm run build
- Deploy command: npx wrangler deploy
- Root directory: /
- Static assets: dist, as configured in wrangler.jsonc
- Build variables: VITE_SUPABASE_URL and VITE_SUPABASE_PUBLISHABLE_KEY, using the existing production project's browser-safe values.

Pushes to ReDesign must be connected to Builds on test4test-redesign. The older
test4test Worker is a separate application; its GitHub build status does not
describe the deployment serving test4test.io. A versions upload creates a
preview and does not publish the production website.

Normal update workflow

1. Run the repository checks required for the change and confirm npm run build succeeds.
2. Commit the intended changes on ReDesign and run git push origin ReDesign.
3. Open test4test-redesign in Cloudflare, then Deployments, and confirm the build
   for the pushed commit succeeds and becomes the active deployment.
4. Verify the changed page at https://test4test.io.

Local .codex-* worktrees and browser profiles are ignored. Never force-add them
to the parent repository: Git records nested worktrees as submodules without
the configuration Cloudflare needs to clone them. To diagnose a recurrence,
inspect git ls-files --stage for mode 160000. Remove accidental local worktree
entries with git rm --cached -- <path>, which preserves the local directory.

Historical preview, promotion, and production cutover runbook

The guidance below describes the original cutover process and future environment
changes. Routine frontend updates use the production configuration above.

1. Preview deployment

- Build a Cloudflare preview from the reviewed redesign commit.
- Build command: npm run build
- Output directory: dist
- Provide only browser-safe variables such as VITE_SUPABASE_URL and VITE_SUPABASE_PUBLISHABLE_KEY.
- Point the preview at an approved preview Supabase environment when validating migrations or destructive workflows.
- Do not add test4test.io to the preview deployment.

2. Preview validation

- Run repository formatting, design-system validation, tests, and production build checks required by the release.
- Validate 390 x 844 and 1440 x 900 interface states, accessibility, auth redirects, public test links, recording capture/upload/playback, transcript lifecycle, clip privacy/revocation, credits, managed orders, retention, cleanup, and rollback.
- Confirm that private recording or thumbnail buckets cannot be browsed and that public clip access returns short-lived media access only after token validation.
- Review marketing claims, package terms, consent, privacy, and support procedures.

3. Branch promotion

- Obtain explicit product, security, accessibility, commercial, and release approval.
- Promote the exact validated commit through the repository’s normal review process to the production branch.
- Do not merge, rebase, or overwrite unrelated uncommitted work as part of deployment preparation.

4. Production deployment

- Build and deploy the promoted production commit, not an unreviewed redesign worktree.
- Apply approved Supabase migrations and Edge Function changes through the release runbook.
- Configure the production Test4Test.io custom domain only after the deployment and backend are ready.
- Set the Supabase Auth Site URL and exact redirect allowlist for https://test4test.io.

5. Cutover and monitoring

- Smoke-test sign-in, create/share, Earn, recording upload/access, transcript processing/retry, clip access/revocation, credits, payment webhooks, managed-order status, account deletion, indefinite finalized-recording retention, and abandoned-draft cleanup.
- Monitor client errors, auth failures, media queues, transcript queues, notification delivery, token abuse, order fulfillment, and cleanup failures.
- Keep a tested rollback target and pause new paid orders if fulfillment or payment state is inconsistent.

Security notes

- Never put Supabase secret/service keys, R2 secrets, worker secrets, SMTP credentials, model keys, or payment secrets in Cloudflare browser variables.
- SPA routing is handled by wrangler.jsonc through assets.not_found_handling = single-page-application.
- Do not add a public/_redirects rule for /index.html; it conflicts with Wrangler SPA handling.
